# vLLM 開源貢獻研究：先看規則，再決定如何驗證

這份研究幫助第一次貢獻 vLLM 的讀者回答三個問題：什麼值得做、要準備哪些證據、送出後怎麼跟進。第一輪先收集官方規範、程式碼與 PR 案例；尚未在本機安裝或測試 vLLM，也沒有認領議題。

研究日期：**2026-11-01**。官方程式碼快照：[`5d55ef1590c92213e3893dc8e8712f7f2e0bc508`](https://github.com/vllm-project/vllm/tree/5d55ef1590c92213e3893dc8e8712f7f2e0bc508)。PR 狀態則以各筆記載的 API 讀取時間為準。

## 第一輪先帶走的判斷

1. **沿用 Ultralytics 的研究方法，但重新查 vLLM 的規則。** vLLM 明文要求 AI 輔助揭露、提交歸屬標註及人的審查責任；大型功能要先走 RFC。詳細條件見[規則筆記](notes/contribution-rules.md)。
2. **先看一個問題能否驗證，再決定要不要接。** `media/` 適合追資料流，但程式是 Python 不代表測試免安裝；單跑媒體測試仍會載入整套測試的共用依賴。Mac 可用範圍目前是[文件與程式碼判讀](notes/code-and-validation.md)，不是本機通過紀錄。
3. **把「看見合併」與「知道為何合併」分開。** 案例可以示範改動與審查，但不能證明某種題目比較容易合併，也不能只憑關閉標籤斷言原因。每件的已知與未知列在[案例筆記](notes/pr-cases.md)。

本書建議下一輪先完成一個 image 測試的環境與執行基線，再擴大範圍。這是依驗證成本提出的研究順序，不是已確認的 bug，也不是維護者指派的工作。

## 如何讀證據

- **官方規則**：以固定 commit 的規範、模板或工作流程為依據。規則改版後需重查。
- **程式碼事實**：說明這個快照實際匯入什麼、測試如何被選入、CI 配置做什麼；不等於執行成功。
- **案例觀察**：可追到 PR、review 或留言。作者回報測試通過，不等於本書自行重現。
- **本書建議**：從前述資料推得的工作順序，需明確標示，不能寫成官方門檻。

[先前的專案比較報告](../oss-candidates/vllm-llamacpp.md)保留為背景資料。本輪沒有重算其中的合併率、回應時間或作者分層；它們不作為本輪已驗證的統計。遇到規則摘要衝突，以本輪固定來源的筆記為準。

## 工作區與編寫方式

這些筆記只存在個人 `research/contribution-book` 分支，**永遠不從研究分支開上游 PR**。正式修正另從更新過的 `upstream/main` 開乾淨分支。候選提案放在[提案總表](../../proposals/README.md)；實跑紀錄放在[教程查核](../tutorial-audit/README.md)或[探測式查核](../probe-audit/README.md)。

文件沿用 ISO 24495-1 的淺白語言原則：讓讀者找得到資訊、讀得懂、能決定下一步。這是編寫原則，不是認證聲明。先保存 Markdown 證據筆記，等內容穩定後再編排章節與建置網站。

本研究使用 AI 分工收集與整理，主 agent 核對來源與交叉檢查。這不取代未來正式投稿者逐行理解、審查與實跑的責任。
