# 分階段收集證據，再整理成貢獻手冊

先讓一條貢獻路徑有可核對的依據，再擴大到統計與完整書籍。本計畫比照 Ultralytics 研究書的問題分類，不假設兩個社群的規則與結果相同。

## 第一輪：規則、驗證成本與案例

本輪產物是三份研究筆記與案例資料，入口見 [README](README.md)。完成標準：主要結論有第一手來源、程式來源固定 commit、案例標示讀取範圍、建議與未驗證事項分開。

| 主題 | 本輪工作 | 後續缺口 |
| --- | --- | --- |
| 貢獻流程、AI 與 DCO | 查官方規範、模板及工作流程 | 正式投稿前重查當時規則 |
| 先開單與 RFC | 分清大型功能、架構變更和小修正 | 具體題目仍要查重與確認預期行為 |
| 程式碼地圖 | 從多模態輸入追到媒體與測試 | 尚未完整涵蓋 scheduler、kernel 等子系統 |
| Mac 驗證 | 讀安裝方式、測試匯入與 CI | 尚未建立環境或實跑 |
| 成功與關閉案例 | 目的性選取少量 PR，讀變更與討論 | 不能推論整體成功率或回應速度 |

## 第二輪：建立一條真實可跑的基線

**已完成（2026-11-01）：** [T01](../tutorial-audit/records/T01.md)記錄官方 CPU 安裝、正常 pytest 收集、圖片／base 共 23 件通過，以及環境版本與日誌。模型服務、音訊、影片與完整 connector 測試仍未驗證。

依[驗證成本筆記](notes/code-and-validation.md)確認當時版本、硬體與安裝方式，再執行一個最小測試。這一輪才開始安裝或建置，第一輪不預填結果。

1. 記錄官方 SHA、Python 與必要套件版本、安裝命令及耗時。
2. 先確認測試能被收集，再跑最小案例；把下載、依賴錯誤和產品錯誤分開。
3. 成功後才擴至同一資料流的其他測試。失敗則記錄第一個阻塞點，不宣稱整個模組不能在 Mac 跑。
4. 將指令、輸入、輸出及限制放進 `research/tutorial-audit/records/`，更新結果表。

**完成標準**：另一人能照紀錄重現至少一個測試結果；或者已用具體錯誤與來源確認阻塞原因。若必須靠無法取得的硬體才能回答問題，就換研究範圍。

## 第三輪：先選題，再決定是否擴大統計

**已完成初探（2026-11-01）：** [P01](../probe-audit/records/P01.md)保存 11 件既有測試、24 組方向案例及 10 組透明背景案例。已重現 PNG 編碼往返方向差異並查重；使用者入口、預期契約及投稿用候選卡仍待完成。

從已能驗證的路徑找一個具體問題。先查現有 issue、open PR 和近期合併，確認預期行為與重現方式，再整理中英提案。查到既有修正就記錄結果，不另做重複 PR。

若要回答「第一次投稿多久有回應、哪些工作較易落地」，另做一輪有取樣定義的研究，不能把本輪選出的案例當分母：

- 先固定建立日期範圍、觀察截止日與納入條件，保留未結案 PR。
- 以投稿前的貢獻歷史定義經驗，不用現在的 `CONTRIBUTOR` 標記倒推。
- 分開作者自關、明確重複、維護者拒絕與原因未知；分類附證據連結。
- 區分首次人類回覆、實質審查和合併時間；交代被截斷或未取完的討論。
- 提供可重算的去敏資料，再比較工作範圍、變更規模和驗證成本。

**完成標準**：先有一張證據完整的候選卡。統計只有在能收齊所需資料時才另行展開；這輪不承諾特定合併數。

## 第四輪：把穩定內容整理成書

候選章節為「準備一筆貢獻」「從症狀找程式」「選題與驗證」「PR 審查案例」「來源與限制」。作者分層、合併率、回應時間及點名 reviewer 的章節，等對應資料完成再加入。

沿用 Ultralytics 的閱讀導向與證據格式；正式建書時再重用既有出版工具。完成標準是來源、內部連結與建置通過，且讀者能從每章找到可執行的下一步。

## 本輪範圍

收集公開資料與本機實跑證據，整理到個人研究分支；不對上游開 issue、留言、認領或開 PR。不將公司、客戶或私人環境資料放入公開研究。
